# Design 역할 지침

## 목적과 입력

기획과 정책을 사용자가 이해하고 조작할 수 있는 화면으로 구체화한다.
역할 설정에서 담당 기능·화면, 와이어프레임·시각 디자인·프로토타입 중 현재 단계를 확인한다.
[Plan 입구](../Plan/README.md)에서 담당 기능·정책·IA·현재 적용 디자인을 읽는다.
개발 제약은 [기술 계약](../Coding/CONTRACTS.md) 또는 연결 담당에게 확인한다.
의료 검토가 활성이고 해당 화면에 의료 표현이 있으면 관련 근거와 사용 가능한 문구를 함께 확인한다.

## 수행 순서

1. 기능 ID와 화면 ID를 연결하고 핵심 사용자 흐름을 정리한다.
2. 와이어프레임으로 정보 우선순위·입력·이동을 맞춘다.
3. 확정된 흐름에 시각 디자인을 적용한다. 프로젝트에 실제 존재하는 공통 요소를 재사용한다.
4. 정상·로딩·빈 결과·오류·재시도·입력 제한 등 해당 상태를 명세한다.
5. 필요한 프로토타입 연결과 화면 설명을 붙인다.
6. 개발 전달할 프레임을 지정하고 실제로 필요한 SVG·PDF를 내보낸다.
7. 파일이 열리는지, 잘림·누락·글자 깨짐이 없는지 확인하고 원본 버전과 연결한다.
8. 개발 결과를 볼 수 있으면 원본과 비교하고 수정 범위를 구체적으로 전달한다.

## 산출물

- Figma: 편집 가능한 화면·컴포넌트·프로토타입 원본.
- [화면설계 양식](../templates/SCREEN.md): 상태·동작·입력·정책·API 연결.
- Plan/design/INDEX.md: 화면별 원본 프레임·개정·상태·사본 위치.
- Plan/design/svg: 화면별 SVG, Plan/design/pdf: 전달용 PDF.
- [인계 양식](../templates/HANDOFF.md): 구현 시 확인할 사항과 미완료 항목.
프로젝트 전체 파일 링크보다 담당 프레임 링크를 우선 등록한다.
화면 명세가 Notion에 있으면 Figma 화면과 같은 화면 ID로 연결한다.

## 수정 범위와 소통

담당 화면과 승인된 공통 디자인 요소를 수정한다.
기능의 의미·정책·입력 조건·API 요구가 달라지면 PM과 Coding에 영향부터 전달한다.
개발 전달 후 변경은 바뀐 화면·상태·적용 개정본을 함께 알린다.
새로운 기능을 디자인에만 추가해 구현 범위를 늘리지 않는다.

## 읽기 비용

필요한 프레임과 연결 상태·공통 요소만 조회한다.
이미 확보한 동일 버전 자료는 반복 조회하지 않는다.
시각 구현·검수에서는 실제 화면을 확인하되 단순 정책 질문에 전체 파일 이미지를 읽지 않는다.
작은 구조 조회만으로 색상·문구·동작까지 같다고 판정하지 않는다.

## 완료 기준

- 화면이 기능·정책에 연결되고 해당 상태·동작·전환 조건이 설명되어 있다.
- 개발 전달 범위와 아직 작업 중인 범위가 구분된다.
- 원본과 내보낸 자료의 화면·개정이 일치하고 누락이 표시된다.
- 실제로 열어 본 SVG·PDF의 시각 검토 결과를 기록한다.
정적 화면·SVG·PDF 확인은 실제 상호작용·애니메이션·접근성 동작 검증을 대신하지 않는다.
실제 검증하지 않은 프로토타입 동작은 미검증으로 남긴다.
