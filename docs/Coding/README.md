# Coding 역할 지침

## 목적과 담당

맡은 기능을 공통 계약에 맞게 구현하고 연결 가능한 상태로 인계한다.
기술 영역(FE·BE·DB·통합 등), 기능, 현재 작업을 따로 확인한다.
'개발자'라는 역할만으로 저장소 전체를 수정하지 않는다.
개발 코드·실행 설정은 기술 스택을 정한 뒤 docs 밖에 둔다.

## 작업 전 읽기

[Plan 입구](../Plan/README.md)에서 담당 기능·정책·완료 기준의 현재 적용본을 읽는다.
[기술 계약](CONTRACTS.md), [통합 현황](INTEGRATION.md), 관련 작업 인계를 확인한다.
의료 기능이 포함되면 관련 근거·적용 조건·확정 문구의 상태도 확인하고 미검토 내용을 검증된 사실로 구현하지 않는다.

| 영역 | 추가 확인 |
|---|---|
| FE | 화면설계·상태·동작, 필요한 Figma 프레임·SVG·PDF, API 요청·응답 |
| BE | 기능 정책, 입력 검증·출력·인증·권한·오류·상태, 데이터 구조 |
| DB | 정보 의미·관계·제약·생성·변경·삭제 규칙과 실제 사용 API |
| 통합 | 실행 순서·필요 설정·연결 계약·핵심 시나리오·잔여 제한 |

## 수행 순서

1. 실제 코드·현재 변경·관련 설정을 확인한다. 코드가 없으면 현황을 없다고 기록한다.
2. 담당 기능과 편집 영역, 입력 자료, 연결 계약, 완료 기준을 맞춘다.
3. 공통 API·데이터 구조는 담당과 변경 범위를 합의한 뒤 확정한다.
4. 계약이 맞으면 각 파트를 병행할 수 있다. mock과 실제 연결 여부를 명시한다.
5. 가장 작은 확인 가능한 기능 단위로 구현한다.
6. 변경에 필요한 빌드·테스트·수동 확인을 실행하고 실패·미검증을 구분한다.
7. [작업 인계 양식](../templates/HANDOFF.md)으로 실제 변경·연결법·검증·제한을 기록한다.
8. 통합 담당과 핵심 흐름을 실행한다. 한 파트 테스트의 성공을 전체 연결 성공으로 표시하지 않는다.

## 계약과 공유 파일

CONTRACTS.md는 연결을 찾는 입구다. 코드·스키마에 있는 정의를 전부 중복 복제하지 않는다.
공개된 계약이 바뀌면 영향 기능·상대 파트·변경 이유·적용 버전을 함께 기록한다.
공통 타입·DB 스키마·루트 실행 설정은 변경 담당을 지정하거나 편집을 순차로 수행한다.
다른 사람의 작업을 되돌리지 않고 자신의 변경을 기존 작업에 맞춘다.
담당 범위 밖 수정이 필요하면 이유·대상·영향을 먼저 전달한다.

## 검증과 완료

명령·환경·대상·실제 결과를 남긴다. 실행하지 않은 명령을 검증 완료로 쓰지 않는다.
화면은 필요한 상태와 실제 동작을 확인하고 서버·데이터 연결도 실제 결과로 구분한다.
FAIL은 원인을 좁혀 수정한 뒤 영향 범위를 재확인한다.
같은 기준·환경·대상에서 유효한 PASS를 이유 없이 반복하지 않는다.
핵심 흐름, 연결 계약, 인계 문서가 맞고 남은 제한이 드러나야 완료 보고할 수 있다.
외부 서비스 실연동·운영 배포·성능을 확인하지 못했다면 미검증으로 남긴다.

## 저장소 작업

현재 기본 브랜치는 main이다. 연결된 비공개 저장소는 [프로젝트 설정](../start/PROJECT_CONFIG.yaml)의 repository 항목에서 확인한다.
Git 초기화·커밋·원격 생성·푸시·병합·배포는 실제 사용자 요청과 확정된 팀 운영 범위에 따른다.
기술 문서 갱신을 이유로 원격을 만들거나 다른 사람의 브랜치를 강제로 변경하지 않는다.
