# PM 역할 지침

## 목적과 범위

팀이 풀 문제, 이번에 만들 범위, 각자의 작업과 최종 시연을 연결한다.
PM이 모든 상세 문서를 혼자 완성한 다음 다른 파트를 시작시키는 방식은 피한다.
실제 인원·아이디어·우선순위·일정·발표 시간은 확인된 내용만 확정한다.

## 작업 전 읽기

[Plan 입구](../Plan/README.md)에서 기획·담당표·기능 목록·정책·관련 결정의 원본을 찾는다.
진행 중 작업이 있다면 Coding의 [통합 문서](../Coding/INTEGRATION.md)와 관련 인계를 읽는다.
전체 과거 기록보다 현재 변경·막힘·의존 작업을 먼저 확인한다.

## 수행 순서

1. 행사 규칙, 사용 가능한 제작 시간, 필수 제출물·발표 조건, 기존 코드·AI 도구 사용 허용 범위를 확인한다.
   미확인은 미정으로 기록하며 행사 안내에 없는 규칙을 만들어 넣지 않는다.
2. 대상 사용자·상황·문제를 정리한다. 관찰 사실, 해석, 가설을 구분한다.
3. 핵심 시연 한 흐름과 필수 기능, 제외 범위를 정한다.
4. 기능 ID를 부여하고 정책·입출력·완료 기준을 합의한다.
5. 사람의 역할·기술 영역·담당 기능·검토자·연결 상대를 담당표에 연결한다.
6. Design이 화면 상세, Coding이 기술 계약, 필요한 검토 담당이 근거를 채우도록 입력을 전달한다.
7. 변경·막힘을 확인하고 범위·순서를 조정한다. 변경 이유와 영향 기능을 결정 기록에 남긴다.
8. 핵심 흐름의 통합 검증과 발표 준비를 조정한다. 실제 구현과 계획을 나누어 설명한다.

## 기능 배정과 병행 작업

배정에는 목적, 담당 사람, 수정 영역, 입력 자료, 의존 작업, 결과물, 완료 기준을 포함한다.
겸임은 가능하지만 현재 작업의 책임은 한 명을 중심으로 정한다.
통합 담당자는 개발 담당 중 조정할 수 있고, PM이라는 이유만으로 자동 배정하지 않는다.
공동 API·데이터 계약과 공통 파일의 변경 담당을 먼저 정한다.
미결정 부분이 있으면 영향을 받는 작업만 대기시키고 독립적인 승인 작업은 진행한다.

## 소통과 인계

변경 시 기능 ID·변경 이유·영향 화면/API·적용 개정본·필요 조치를 짧게 전달한다.
기능별 원본에 작업 중 / 개발 전달 완료를 표시하고 전달한 기준을 알린다.
기획을 내보낼 때 관련 정책·담당표·화면 연결이 맞는지 확인한다.
[공통 인계](../templates/HANDOFF.md)의 완료·검증·미완료 구분을 사용한다.

## 완료 기준

- 핵심 기능의 목적·범위·정책·담당·완료 기준이 연결되어 있다.
- 미정과 가설이 사실처럼 쓰이지 않았고 제외 범위가 명확하다.
- 팀원이 담당 문서와 원본·백업을 찾을 수 있다.
- 시연 결과·잔여 결함·발표 주장이 실제 결과와 맞는다.
- 온라인 원본·백업의 개정과 누락 상태가 기록되어 있다.
발표·배포·제출 자체는 실제 요청된 범위와 제출 조건에 따라 수행한다.
